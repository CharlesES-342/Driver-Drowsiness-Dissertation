\section{Back-End:}
\paragraph{Network Architecture and Hosting}
By utilizing Raspberry Pi OS (Desktop), I can easily toggle between “Hotspot Mode” for device testing and “WI-FI Client Mode” for pulling
updates via Git. This flexibility of duel purpose drastically accelerated the development and testing cycle of this section of the project,
with the ease of not needing to type commands or form a toggle file.
\paragraph{Initial Flask Implementation}
To validate the connection, I developed a light-weight Flask application to serve a basic index.html file. This contained no information,
images or other resources, just text. This confirmed that devices could successfully connect to the Pi’s hotspot and access the web
server by inputting the Pi’s IP address.
This application was constructed to specifically use \texttt{port 80} (HTTP), removing the need to define the connection protocols when handling
IP addresses (Such as when changing the hostname)
\paragraph{Local DNS Resolution}
To provide a seamless user experience, I wanted to remove the IP-based navigation and instead navigate with a custom hostname. To do this
I used \texttt{dnsmasq}. Using this, I configured the domain \textbf{“drowsiness”} directly to the local IP address for the application.
\paragraph{Performance Optimisers (DNS Upstream)}
Since the system operates as an offline connection, with no external internet access, I disabled recursive DNS lookups\footnote{the
process where a device tries to ask other (more senior) servers for corresponding IP addresses for addresses outside of its local
scope/knowledge}.
This improves the performance by preventing the Pi from attempting to contact upstream servers for un-known queries, eliminating the
latency caused by waiting for timeout responses.
However, with this in mind, it is important that this change is reverted when connecting to the wider internet as this can prevent you
from accessing resources such as the GitHub repository. To revert simply remove “no-resolv” from \texttt{/etc/dnsmasq.conf}. This will
allow the device to now look towards up-stream providers in the event a webpage cannot be found.

\paragraph{Multi-User Scalability}
To allow for multiple devices to connect at once, I configured a /24 subnet mask to manage IP assignments. While the Raspberry Pi’s hardware
typically supports 5-10 devices connected concurrently, this ensures that:
\begin{itemize}
    \item Multiple passengers can connect without causing IP conflicts
    \item The driver’s connection remains stable, ensuring that safety critical data is always accessible, even if other devices accidently
    “auto-join” the network
\end{itemize}

\paragraph{Reverse Proxy}
To further the reliability and security of the device, a \textbf{Rexerse Proxy - (Nginx)} \footnote{This is a layer of protection between the
applicaiton and users which aims to protect the server (Raspberry Pi)} is used.
Then, to resolve the resource race between the\textbf{NetworkManager} and \textbf{dnsmasq}, the internal DNS capabilities of the NetworkManager
were disabled. \\

This ensures that dnsmasq has exclusive control over domain name resolution and IP management, forming a more stable environment.

\paragraph{API}
As previously mentioned, I have opted for an integrated API and AI model solution, where the model work to use in-memory state management rather than a database or file; the main reasons being to reduce complexity by avoiding I/O overhead provided from databases
and avoid race conditions.

\paragraph{Structure}
The API file will be broken into 3 sections for simplicity and ease of use:
\begin{itemize}
    \item\textbf{Flask Initialization}
        To ensure the system is "headless" and user-ready upon booting, the Flask application is initialized within the main execution
        script. While the web server and the core logic could be decoupled, integrating them here ensures that all dependencies are
        functional before the system enters its operational state. Furthermore, this centralized initialization allows for the
        asynchronous loading of resource-heavy components, such as the AI model, ensuring the web interface is responsive while the
        backend completes its setup.
    \item\textbf{Prediction Generation}
        To maintain a real-time "safety-critical" stream, the AI model runs on a dedicated background thread. This decoupling is vital
        for multi-user support; without threading, independent API calls from multiple web clients would block the main execution
        loop, causing the model to drop frames and increasing system latency. To prevent race conditions during data exchange between
        the inference engine and the API endpoints, \texttt{threading.Lock()} is implemented. This ensures thread-safe access to shared
        variables, allowing one process to update the prediction data while others read it without data corruption.
    \item\textbf{Web Call Processing}
        The system utilizes relative URL routing for API requests rather than hardcoded IP addresses, which ensures the interface
        remains functional regardless of the network environment or the specific IP assigned to the Raspberry Pi. 
\end{itemize}

\paragraph{Package and Data-Transfer}
Cache-Control is required to ensure that the system remains up-to-date and safety is paramount. This is done by teh following Modern Header Controlls:
\begin{itemize}
    \item \textbf{no-chache:} forces the webpage receiving/requesting the data to check with the server before using the cached version of the data
    \item \textbf{no-store:} tells teh browser to \textbf{never} save any part ofm the request or response to the local disk
    \item \textbf{must-revalidata} reinforces the no-cache. Tells teh browser that once data becomes 'stale' (imediatelly) it can no longer be used
\end{itemize}

To help support older borwsers (in the event the user has an older device), Legacy Headers are also used:
\begin{itemize}
    \item \textbf{Progma: no-cache} Check with the server before using the cached version of the data
    \item \textbf{Expired: 0} sets an expiration date to the begining of th etime count (01/01/9070), since all dates are now after that, it means the
    data will be expired instantly
\end{itemize}

\section{Enabling on Boot:}
Since this is to be a 'headless' system, it is importaint for the program to run automatically (e.g. when the vehicle is turned on). Since general cigarette lighter power cables
provide the 5V necessary for the Pi to function as intended, this can be used to power the system, however, without a display (thus far), you cannot enable the program. To recrify
this, a \textbf{.service} file will be used. This has three sections:
\begin{itemize}
    \item \textbf{[Unit]} - Acts as the metadata and dependency layer. It provides a description for debugging during status checks and defines the boot order. In this case, it
    includes a \textbf{soft dependency} (\texttt{Wants=network-online.target}) to ensure the system attempts to establish a connection before the script runs, while also ensuring
    the script only starts once the system is fully initialized.
    
    \item \textbf{[Service]} - This is the "execution" layer that defines \textit{how} the script runs. It specifies the command to execute the Python script, the working directory,
    and the specific user permissions to ensure the script does not run with unnecessary root privileges. Crucially for a headless system, it handles
    \textbf{error recovery} via the \texttt{Restart} parameter, which automatically re-launches the program if it crashes or fails. I choose a delay period of 10-seconds becuase
    it allows me to rectify any issues (e.g. the camera becoming unplugged)
    
    \item \textbf{[Install]} - This section handles the "integration" of the service into the system's boot sequence. By using the \texttt{multi-user.target}, it tells the Raspberry
    Pi to link this service to the standard startup routine. This ensures that as soon as the Pi receives power from the vehicle and reaches its normal operating state, the service
    is triggered without any manual user intervention. This helps to ensure that the safe normal start-up occures correctly before the program is run.
\end{itemize}
